# W2 수집기 — 설계

랜딩 이전 단계입니다. 이 문서가 정하는 것은 **무엇을 언제 호출하고, 실패를 어떻게
분류하고, S3에 어떤 키로 쓰는가**까지입니다. 적재(`raw.*`)는 W3이고
[`docs/model/decisions.md`](../model/decisions.md)가 소유합니다.

> 수집기 코드는 **이 리포에 없습니다.** 전용 리포(`*-collector`)에 분리합니다 — 근거는 §1.
> 이 문서는 포트폴리오 쪽에 남는 설계 기록이고, 수집 리포 README가 여기를 링크합니다.

---

## 1. 왜 전용 리포인가

GitHub Actions를 10분 주기 cron으로 쓰는 것은 약관 해석에 노출된 선택입니다
(보드가 리스크를 인지하고 감수 결정). 제재 수단 원문이
**"disable repositories, or suspend accounts"** — 즉 가벼운 제재는 **리포 단위**입니다.

수집 워크플로를 포트폴리오 리포에서 분리하면 리포 단위 제재가 **최종 산출물을 비껴갑니다.**
비용은 리포 하나이고, 포트폴리오에서 수집 코드가 안 보이는 손실은 이 문서와 README 링크로 메꿉니다.

계정 단위 제재까지 가면 분리로는 막지 못합니다 → 포트폴리오 리포의 제2 백업이 유일한 대비입니다(§6 결정 5).
**두 번째 무료 계정을 만드는 것은 대비가 아니라 위반을 하나 더 쌓는 것입니다** —
ToS 원문이 "no more than one free Account"입니다.

## 2. 실측한 소스 사실

측정하지 않은 것은 §7에 따로 모았습니다. 추측을 규칙으로 올리지 않습니다.

### 2.1 자전거 — `list_total_count`로 페이지 수를 결정할 수 없습니다

```
GET /sample/json/bikeList/1/5/
→ {"rentBikeStatus":{"list_total_count":5, "RESULT":{"CODE":"INFO-000"}, "row":[...5건]}}

GET /sample/json/bikeList/1/1000/
→ <RESULT><CODE>ERROR-335</CODE>… 샘플키는 한번에 최대 5건
```

`list_total_count`가 **5**로 왔습니다. 요청 범위 크기와 같아서
**"전체 대여소 수"인지 "이 응답의 반환 건수"인지 구별되지 않습니다.**
sample 키는 범위를 1~5로 강제하므로 정식 키 없이는 이 모호성을 해소할 수 없습니다.

→ **페이지 루프 종료 조건을 `list_total_count`에 걸지 않습니다.** `len(row)`로 판정합니다(§3 R2).
이 필드를 믿고 쓰면, 그 의미가 "반환 건수"였을 때 **첫 페이지에서 루프가 끝나고
수집은 조용히 성공합니다** — 2,400개 대여소가 사라진 채로요. 테스트로 안 잡힙니다.

### 2.2 ⚠️ 호출 횟수가 확정판 §9.1의 432회 전제를 깹니다

서울 OpenAPI는 **1회 응답 최대 1,000건**이고, `bikeStationMaster` 실측이 **3,434건**입니다.
운영 중 대여소가 3,000개를 넘으면 스냅샷당 3회가 아니라 **4회**입니다.

| 운영 대여소 수 | 스냅샷당 호출 | `*/10` (144슬롯/일) | `*/15` (96슬롯/일) |
|---|---|---|---|
| ≤ 3,000 | 3 | 432 | 288 |
| 3,001 ~ 4,000 | **4** | **576** | 384 |

확정판이 적어둔 **일 432회는 ≤3,000을 전제한 값**입니다. 마스터가 3,434건이므로
**576회 쪽이 더 그럴듯합니다** — 마스터에는 폐지 대여소가 섞여 있어 확정은 아니고,
측정 ④가 이 값을 정합니다.

**§9.1의 판정 규칙은 그대로 유효합니다.** 450회 연속 호출에서 `ERROR-337`이 1회라도 나오면
`*/15`로 내리고, 그때 호출은 384회가 되어 450 아래입니다. 다만 **576회가 사실이면
`*/10`은 450회 시험선을 이미 넘어서 있으므로, 측정 ④와 ⑤를 같은 날에 봐야 합니다.**
④가 4페이지로 나오고 ⑤가 0회라면, 쿼터가 576보다 크다는 것까지 확인된 것은 아닙니다 —
450회까지만 확인된 것입니다.

### 2.3 ASOS — 실패 응답이 정상 응답과 다른 봉투로 옵니다

```
키 없음  → HTTP 401  {"OpenAPI_ServiceResponse":{"cmmMsgHeader":{
                        "errMsg":"SERVICE_KEY_IS_NULL","returnReasonCode":"20"}}}
키 틀림  → HTTP 403  {"OpenAPI_ServiceResponse":{"cmmMsgHeader":{
                        "errMsg":"SERVICE_KEY_IS_NOT_REGISTERED_ERROR","returnReasonCode":"30"}}}
정상     →           {"response":{"header":{"resultCode":"00"},"body":{"items":…}}}
```

`response.body.items`를 기대하는 파서는 실패 응답에서 `KeyError`로 죽습니다.
**봉투를 먼저 보고 분기해야 합니다** — `OpenAPI_ServiceResponse` 키가 있으면 즉시 실패입니다.

두 에러는 **성질이 같습니다 — 재시도로 절대 풀리지 않습니다.** 미승인이거나 키가 틀렸거나
Encoding 키를 라이브러리로 한 번 더 인코딩한 것이고, 셋 다 사람이 고쳐야 합니다.
재시도를 걸면 쿼터만 태웁니다.

### 2.4 자전거 — 오류 응답이 `/json/` 경로에서도 XML입니다

위 `ERROR-335` 응답이 그 증거입니다. 경로에 `json`이 들어 있어도 실패는 XML로 옵니다.
그리고 트랙 B 실측에서 **실패도 HTTP 200**으로 왔습니다(본문에 `ERROR-500`).

→ **상태코드로 성공을 판정하지 않습니다.** 응답 첫 바이트가 `<`인지 보고 XML이면 `RESULT/CODE`,
JSON이면 `RESULT.CODE`를 읽어 판정합니다.

## 3. 확정 규칙

본인이 다르게 정할 수 있는 것은 §6으로 뺐습니다. 여기 있는 것은 실측이나 기존 결정에서
기계적으로 따라오는 것들입니다.

### R1. 재시도 분류표 — 이게 W2의 핵심 산출물입니다

| 소스 | 신호 | 의미 | 재시도 |
|---|---|---|---|
| 자전거 | HTTP ≠ 200, 타임아웃, 연결 실패 | 전송 실패 | ✅ 지수 백오프 |
| 자전거 | 본문 `INFO-000` | 성공 | — |
| 자전거 | `INFO-200` | 데이터 없음 — **정상 빈 결과** | ❌ 오류로 세지 않음 |
| 자전거 | **`ERROR-337`** | **일일 쿼터 소진** | ❌ **즉시 중단 + 주기 하향 판정(§9.1)** |
| 자전거 | `INFO-100` / `ERROR-300` / `ERROR-335` | 설정·키 오류 | ❌ 즉시 실패, 사람이 고침 |
| 자전거 | `ERROR-500` 등 서버측 | 일시 장애 | ✅ |
| ASOS | `OpenAPI_ServiceResponse` 봉투 + 401/403 | 키 미주입·미승인·인코딩 | ❌ 즉시 실패 |
| ASOS | `resultCode == "00"` | 성공 | — |
| ASOS | `resultCode == "03"` (NODATA) | D-1 미공개 — **정상 빈 결과** | ❌ 다음 일차 실행이 메움(R5) |
| ASOS | 쿼터 초과 (`returnReasonCode` 22 계열) | 쿼터 | ❌ (**미실측** — §7) |

**`ERROR-337`을 재시도 목록에 넣으면 쿼터 소진 1건이 N건이 됩니다.** 재시도의 목적은
일시적 장애를 넘기는 것이고 쿼터는 일시적이지 않습니다. W2 검증 기준이 이 항목을
따로 확인하는 이유입니다.

**"정상 빈 결과"를 오류로 처리하지 않는 것도 같은 무게입니다.** `INFO-200`을 실패로 세면
워크플로가 빨간불이 되고, 빨간불이 일상이 되면 진짜 고장을 못 봅니다.

### R2. 페이지 루프 종료 조건

```
범위 크기 1000으로 1/1000, 1001/2000, … 순차 호출
종료:  len(row) < 1000  또는  INFO-200
```

`list_total_count`를 쓰지 않습니다(§2.1). 페이지 수를 상수로 고정하지도 않습니다 —
신규 대여소가 쌓여 경계를 넘는 순간 **조용히 잘립니다.**

### R3. 슬롯 하나 = S3 객체 하나 — 부분 커밋이 구조적으로 불가능해집니다

전 페이지를 메모리에서 합쳐 **슬롯당 gzip 객체 1개**로 올립니다.
한 페이지라도 실패하면 **아무것도 올리지 않습니다.**

```
raw/bike_status/dt=2026-11-07/hh=03/slot=20261107T0330Z.json.gz
raw/weather_hourly/dt=2026-11-06/obs=20261106.json.gz
```

**이것이 `decisions.md` D2의 승계 조건입니다.** D2는 중복 슬롯에서 `DO NOTHING`
(먼저 쓴 행이 이긴다)을 골랐고, 그 선택이 안전한 것은 **"먼저 쓴 행"이 항상 완전한
슬롯일 때만**입니다. 부분 페이지가 커밋될 수 있으면 D2는 *더 나쁜 관측이 영구히 남는*
최악의 선택으로 바뀝니다. 객체를 하나로 두면 S3 `PutObject`의 원자성이 그 보장을 공짜로 줍니다.

- 3,434행 × 약 150B ≈ **500KB** (gzip 후 더 작음) — 메모리·업로드 모두 문제없는 규모
- 키가 `slot_ts`에서 결정적으로 나오므로 **재실행은 덮어쓰기**이고 중복 객체가 생기지 않습니다
- `dt=`/`hh=` Hive 레이아웃 — W5에서 파티션 프루닝이 그대로 걸립니다

대안(페이지별 객체 + `manifest.json`을 마지막에)은 슬롯당 용량이 커졌을 때의 경로로만 남깁니다.
지금 규모에서 선택할 이유가 없고, 로더가 manifest 유무를 확인하는 분기를 하나 더 져야 합니다.

### R4. 타임존 — `slot_ts`는 UTC, 변환 지점은 한 곳

| 지점 | 처리 |
|---|---|
| Actions 러너 | **UTC** — 변환 없음. 호출 시각을 10분 floor → `slot_ts` |
| ASOS `tm` | **KST** → UTC 변환 **여기 한 번만** |
| 랜딩 저장 | `timestamptz` UTC |
| `date_key` 계산 | dbt에서 KST로 — 유일한 역변환 지점 |

`decisions.md` D1과 네 곳이 같아야 합니다. W1 리뷰에서 **미착수**로 남은 항목이고,
수집기가 생기면 판정 대상이 됩니다.

### R5. ASOS는 D-3 ~ D-1을 매일 가져옵니다 — 결측이 스스로 메워집니다

하루 1회 실행에서 **최근 3일 구간**을 요청합니다. PK가 `(stn_id, obs_ts)`이므로
겹치는 날은 적재 단계에서 걸러지고, **한 번 건너뛴 날이 다음 실행에서 자동 복구**됩니다.

비용은 호출 1회(numOfRows를 72로)이고, 얻는 것은 **백필 경로를 따로 만들지 않아도 되는 것**입니다.
`resultCode 03`(미공개)도 이 구조에서는 다음 날 해결되므로 실패가 아닙니다.

> 자전거 쪽은 이게 **불가능합니다.** 실시간 대여정보에 과거 시점 조회 수단이 없습니다 —
> 건너뛴 슬롯은 영구 소실입니다. 그래서 자전거는 복구가 아니라 탐지·기준선 쪽으로 대응합니다(§4).

### R6. 의존성 설치 0 · Actions 전용 API 비의존

- 호출·압축은 **표준 라이브러리**(`urllib`, `gzip`), 업로드는 러너 프리인스톨 `aws s3 cp`
  → `pip install` 단계가 사라져 job이 수십 초로 끝납니다. 약관 판단 기준이 "서버 부담"이므로
  이건 비용 절감이 아니라 **노출 축소**입니다
- 수집 로직은 `GITHUB_*` 환경변수나 Actions 전용 출력 규약을 **쓰지 않습니다.**
  설정은 전부 환경변수, 진입점은 `python -m collector` 하나
- `timeout-minutes: 5` + `concurrency` 그룹 — 공식 job 한도가 6시간이라 기본값에 맡기면
  사고 시 6시간을 태웁니다
- OIDC 역할은 CI용과 **분리**하고 수집용은 해당 프리픽스 `PutObject`만

**R6의 마지막 항목이 이 환경 결정을 가역적으로 만듭니다.** 환경을 옮길 일이 생기면
패키징 변경으로 끝나고, 수집기를 다시 쓰지 않습니다.

## 4. 완결성은 144/일이 아니라 실측 기준선으로 판정합니다

144 고정값을 쓰면 테스트가 상시 실패해 **의미 없는 빨간불**이 됩니다
(Actions cron은 best-effort이고 현재 지연이 관측되는 중입니다).

| 임계 | 값 |
|---|---|
| 기준선 | W1 파일럿 24h **실측 확보 슬롯 수** |
| `warn_after` | 기준선의 **90%** |
| `error_after` | 기준선의 **70%** |

2단으로 두는 이유는 **평시 변동(warn)과 고장(error)을 분리**하는 것입니다. 한 칸이면
상시 빨간불 아니면 무용지물 둘 중 하나가 됩니다.

**드리프트는 버리지 않고 데이터로 남습니다** — `slot_ts`(10분 floor)와 `fetched_at`(실제 호출 시각)의
차이가 스케줄러 드리프트이고, 두 필드는 이미 랜딩에 있습니다. 분포 한 장을 README에 넣으면
리스크가 **측정 결과**로 바뀝니다. 추가 작업 0입니다.

**"실행이 아예 생성되지 않는" 고장은 워크플로 실패 알림이 오지 않습니다**(실패한 run이 없으므로).
이 사각지대는 `_sources.yml`의 freshness가 메우고, 임계는 위 기준선에 맞춥니다.

## 7. 확인하지 못한 것

추정치를 넣지 않았습니다. 전부 정식 키가 있어야 풀립니다.

1. **`list_total_count`의 의미** — 전체 건수인지 반환 건수인지. R2가 이걸 안 쓰므로 설계를 막지는 않습니다
2. **운영 중 대여소 수** = 페이지 수 (측정 ④). §2.2의 호출 예산이 여기 걸려 있습니다
3. **실제 일일 쿼터** — 공식 문서에서 `bikeList`의 공통 한도를 찾지 못했습니다.
   측정 ⑤(450회 연속 호출)가 알아내는 수단이고, **450 위쪽은 그 측정으로도 모릅니다**(§2.2)
4. **ASOS 쿼터 초과 응답의 정확한 형태** — 개발계정 트래픽 10,000건이라 파일럿에서 닿지 않습니다
5. **마지막 페이지를 넘긴 호출의 응답** — `INFO-200`인지 `ERROR-300`인지. 결정 2를 ①로 두면 안 닿습니다
6. **"repository activity"의 정의와 60일 비활성화 알림 여부** — 두 공식 문서에 정의도 알림 문구도 없습니다

## 8. W2 통과 조건

리뷰 체크리스트 전문은 산출물보다 **먼저** 작성해 Paperclip PAR-1 문서
(`W2 수집기 — 리뷰 기준`)에 올려뒀습니다. 기준을 나중에 만들면 사후 정당화이고,
그 차이는 말이 아니라 작성 순서로만 증명됩니다. 통과 조건 요약은 다음과 같습니다.

- staging에서 `(station_id, slot_ts)` 유일성 테스트 통과
- pytest 통과
- **장애 주입 로그** — 소스 5xx에서 재시도, `ERROR-337`에서 재시도하지 **않음**
- **페이지 중간 실패 주입 시 S3에 부분 슬롯 객체 0건** (D2 승계 조건)
- 수집기가 Actions 전용 API에 의존하지 않음 — 로컬에서 `python -m collector`로 동일 동작
- 24시간 연속 가동. 판정은 144슬롯이 아니라 **파일럿 실측 확보율 대비 달성률**
